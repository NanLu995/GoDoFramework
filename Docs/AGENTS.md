# Docs 协作规则

> 文档类型：工作流
> 状态：当前
> 权威范围：`Docs/` 下内部文档的维护规则
> 最近核对：2026-09-28
> 相关入口：[根协作规则](../AGENTS.md)、[内部文档入口](README.md)

本文件适用于 `Docs/` 下的内部项目文档；根目录 `AGENTS.md` 仍是最高约束。

## 文档状态

- **当前**：已经采用且需要与实现同步的事实或流程。
- **草案**：仍在讨论，不能作为实现授权。
- **验证中**：实现已经存在，但稳定性或平台证据仍未收敛。
- **仅供参考**：研究、外部对比或历史材料，不建立项目需求。

每份管理文档开头写明文档类型、状态、权威范围和最近核对日期。研究文档必须明确标注“仅供参考”。

## 修改规则

1. 先判断内容属于当前事实、计划、设计、工作流还是研究，不在同一段落混写不同状态。
2. API、失败语义、生命周期、性能和详细验证只在模块 `USAGE.md` 维护；项目文档使用链接和摘要。
3. 架构基线只记录已经采用的跨模块事实；候选方向进入路线图或设计文档。
4. `当前开发.md` 只保留一个主要目标；长期候选进入路线图，未决取舍进入待确认问题。
5. 重要决定追加到决策日志。改变既有决定时新增记录并注明替代关系，不静默改写历史理由。
6. 问题解决后，从待确认问题移除并链接到对应决策或实现证据。
7. 研究结论只有经过明确决策和立项后，才能进入路线图、架构基线或实现。
8. 修改内部路径时同步更新根目录 `README.md`、`AGENTS.md`、相关技能说明和仓库内引用。

## 冲突处理

文档与源码、配置或测试冲突时，以可复核的实现证据为准，并在同一任务中修正文档。无法确认时，把问题登记到 `00_项目/待确认问题.md`，不得把推测写成当前事实。

`PublicDocs/` 与内部文档职责不同，不能把内部设计稿直接加入公开站点，也不能用公开教程替代内部架构和进度记录。
