# GoDoFramework 框架能力评估

> 文档类型：研究
> 状态：仅供参考
> 权威范围：保留通用框架能力清单对 GoDoFramework 的评估结论，不建立实现需求
> 最近核对：2026-09-28
> 相关事实：[架构基线](../01_架构/架构基线.md)、[模块状态](../00_项目/模块状态.md)

本文件是早期通用框架模块参考的收口结果。原始长篇清单已经删除；其有效判断保留于此，原文仍可从 Git 历史恢复。当前实现事实以源码、工程配置、测试和模块 `USAGE.md` 为准。

## 1. 结论

GoDoFramework 已覆盖当前定位所需的主要跨游戏机制。现阶段应收敛现有模块、补真实项目和目标平台证据，而不是按通用框架清单继续增加模块。

评估时必须区分：

- 模块不存在，不代表框架缺陷；玩法、产品和特定技术栈能力通常应留在业务或可选包。
- 模块已经存在，不代表所有扩展方向都已实现或应该进入同一模块。
- 研究中的候选项只有经过真实需求、独立设计和明确确认后，才能进入路线图或实现。

## 2. 已采用的边界

| 能力 | 当前取舍 | 证据入口 |
|---|---|---|
| 启动与长期服务 | GoDoRuntime 显式注册并按依赖安全顺序关闭，不承载业务流程 | [架构基线](../01_架构/架构基线.md) |
| 模块协作 | 显式依赖、EventChannel 和业务侧 Services；不引入通用 DI | [架构基线](../01_架构/架构基线.md) |
| 时间与异步 | Scheduler 处理游戏时间调度；Godot 信号和可取消异步处理流程 | [Scheduler](../../addons/godo_framework/Runtime/Scheduler/USAGE.md) |
| 资源与对象生命周期 | ResourceHub 使用 Godot Resource 边界；NodePool 管理节点复用 | [ResourceHub](../../addons/godo_framework/Runtime/Resources/USAGE.md)、[NodePool](../../addons/godo_framework/Runtime/Pool/USAGE.md) |
| 场景与顶层流程 | Scene 负责主内容场景，Procedure 负责编排业务阶段 | [Scene](../../addons/godo_framework/Runtime/Scene/USAGE.md)、[Procedure](../../addons/godo_framework/Runtime/Procedure/USAGE.md) |
| 局部状态 | 轻量 `StateMachine<TContext, TState>` 处理同步局部状态，不统一所有系统 | [StateMachine](../../addons/godo_framework/Runtime/StateMachine/USAGE.md) |
| UI、音频、输入与相机 | 提供跨项目机制；具体表现、玩法规则和内容选择留给业务 | 对应 Runtime 模块 `USAGE.md` |
| 配置、数据、存档与设置 | Config、DataTable、Save、Settings 各自维护明确边界 | 对应 Runtime 或 Tool 模块 `USAGE.md` |
| 诊断与质量 | ErrorHub、LogHub、Debugger、自动回归和发布门禁提供工程证据 | 对应模块 `USAGE.md` 与 [发布说明](../../release/README.md) |

## 3. 仍需验证或由真实需求触发

以下内容不是当前需求或承诺：

| 方向 | 立项前需要的输入 |
|---|---|
| 应用前后台、窗口失焦、暂停恢复和低内存事实 | 明确目标平台，并核对 Godot 通知语义和业务恢复策略 |
| 可访问性基线 | 至少一个真实项目提出字体、对比度、字幕、输入替代或屏幕阅读需求 |
| 技术遥测与崩溃上下文 | 明确采集目标、隐私边界、Reporter 后端和平台限制 |
| 配置差异与更多构建期校验 | 出现可重复的配置错误，并确认规则能跨项目复用 |
| Camera 第二视角 | 明确 2D/3D、SubViewport 所有权、渲染层、分辨率和更新频率 |
| Audio 2D 空间线路 | 出现实际 2D 游戏场景，并给出并发、距离和总线需求 |
| 远程资源、PCK/DLC 或热更新 | 明确下载、校验、挂载、回滚、磁盘和安全要求 |
| 网络传输层 | 至少一个真实在线项目明确协议、平台、鉴权和失败恢复要求 |

这些输入统一记录在[待确认问题](../00_项目/待确认问题.md)或独立设计文档中，不直接从研究资料转成待办。

## 4. 明确不进入当前核心

- 角色、属性、Buff、技能、战斗、任务、成就、对话、背包、商城等玩法或产品系统。
- 通用 Network、AI、HFSM、全系统统一状态机、ECS 或虚拟文件系统框架。
- ResourceHub 的第二套缓存、引用计数、LRU、手动 Release 或远程下载职责。
- 强制 MVVM、红点、商城、引导和具体 Loading/Toast 表现集合。
- 自动程序集扫描、反射式插件发现、隐式依赖注入和全局大门面。
- 修改运行时状态的 GM 控制台；Debugger 保持只读。

Friflo ECS 已作为可选集成存在，不改变“ECS 不进入 GoDo 核心”的结论。

## 5. 立项判断

候选能力进入路线图前必须同时回答：

1. 哪个重复痛点已经在真实项目出现？
2. Godot 原生能力和现有 GoDo 模块为什么不足？
3. 负责什么，明确不负责什么？
4. 所有权、生命周期、线程、失败语义和性能预算是什么？
5. 是否形成第二套缓存、调度或生命周期？
6. 哪些自动化、Godot 场景和目标平台证据可以验收？

无法回答时保持候选或暂缓，不为“模块齐全”立项。
