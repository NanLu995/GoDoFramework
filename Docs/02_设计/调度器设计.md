# SchedulerService 设计

> 文档类型：设计
> 状态：验证中
> 权威范围：Scheduler 的设计目标、关键取舍和剩余验证；API 与验证明细以模块 `USAGE.md` 为准
> 最近核对：2026-09-28
> 相关契约：[Scheduler USAGE](../../addons/godo_framework/Runtime/Scheduler/USAGE.md)

## 1. 问题与目标

Godot `Timer` 适合场景内局部计时，但跨流程的延迟、重复调度和异步等待还需要统一回答：

- 使用游戏时间、非缩放游戏时间还是真实时间；
- 在 Process 还是 Physics 阶段派发；
- 暂停、卡帧、场景退出和框架关闭时如何处理；
- 回调失败是否影响其他任务；
- 如何避免为每个任务创建 Node。

Scheduler 只统一主线程上的调度语义，不替代引擎动画、后台任务或确定性模拟。

## 2. 非目标

- 确定性 Tick、网络同步时钟或回滚模拟。
- 后台线程执行器和通用协程框架。
- Tween、动画、音频采样级高精度计时。
- 日历提醒、离线收益和跨存档持久化。
- 自动重试、业务队列或任务依赖图。

## 3. 已确认方案

### 时间与阶段

- `GameTime` 受 SceneTree 暂停和 `TimeScale` 影响。
- `UnscaledGameTime` 不受 `TimeScale` 影响，但仍遵守游戏暂停。
- `RealTime` 使用单调时间，不受暂停或 `TimeScale` 影响。
- Process 与 Physics 分开推进，任务只在选定阶段派发。

### 调度语义

- 0 秒任务最早在下一次对应更新派发，不同步重入。
- 同到期任务保持稳定顺序。
- 重入创建和取消在当前派发边界安全生效。
- 重复任务首次执行等待完整间隔；卡帧遗漏周期合并为一次，不追赶补发。
- 独立暂停保存任务自身时钟中的剩余时间，恢复后继续等待。
- Owner 必须是已进入场景树的有效 Node；退出树时自动取消关联任务。
- Owner 为空表示任务允许跨场景，清理由调用方负责。

### 异步与线程

- `DelayAsync` 与回调调度使用同一套时钟、阶段和 Owner 语义。
- 服务 API 只允许 Godot 主线程调用。
- `CancellationToken` 可以从后台线程触发，但取消在下一次主线程更新提交。
- 框架关闭会取消全部任务和未完成等待。

### 失败与诊断

- 参数和生命周期误用立即抛出明确异常。
- 单个回调异常由 ErrorHub 隔离；异常的重复任务终止，不影响后续任务。
- Debug 快照只在查询时遍历活动任务，Release 不包含快照状态。
- GoDo Debugger 的 `运行时 / Scheduler` 页面按需展示任务分布、活动任务和最近结束原因。

## 4. 数据结构与性能取舍

人工时钟核心按“时钟 × 阶段”维护优先队列。无任务到期时只检查队首；取消产生的失效项按受控条件压缩，不在每帧扫描全部任务。

设计目标：

- 稳定等待帧零托管分配；
- 活动任务数量决定查询成本，Debug 明细有固定上限；
- 创建任务和 `DelayAsync` 允许必要分配；
- 不为每个任务创建 Godot Node。

具体基准规模、数值和命令维护在模块 `USAGE.md` 与 `Verification/Performance/README.md`，本文件不复制。

## 5. 生命周期接入

SchedulerService 由 `GoDoRuntime.tscn` 声明为长期子节点，由 Godot 驱动 Process / Physics Process；GoDoRuntime 负责获取、注册和关闭。业务通过 `ISchedulerService` 使用，不自行实例化或重复注册。退出时先关闭 Scheduler 并取消未完成任务，再清理其他服务。

## 6. 剩余验证

首版实现、自动回归、Windows Demo3D 人工验收和 Debugger 页面已经完成。提升为稳定基线前仍需：

- 至少一个真实游戏长期使用后的 API 和误用反馈；
- 非 Windows 目标平台的暂停、失焦和单调时间行为；
- 目标平台上的规模与分配复核。

当前成熟阶段以[模块状态](../00_项目/模块状态.md)为准。
