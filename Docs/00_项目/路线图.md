## 阶段路线

| 阶段 | 目标 | 当前结论 |
|---|---|---|
| 0. 基线整理 | 文档、边界和测试入口一致 | 已完成，继续随变更维护 |
| 1. 稳定 Core | EventChannel、ErrorHub、Services、GoDoRuntime 可长期依赖 | 已纳入基线 |
| 2. 高频运行时能力 | Resources、Pool、Scene、Audio | 核心能力已纳入基线；扩展能力继续验证 |
| 3. 数据与产品能力 | Save、Settings、Config、Localization、DataTable | 首版均已存在；移动端、AOT 和真实业务继续验证 |
| 4. 开发体验 | Debugger、UI、EditorPlugin 和安装检查 | 首版已存在；工作流继续通过真实项目收敛 |
| 5. 流程与输入 | Procedure、StateMachine、Scheduler、Input | 首版已存在；继续收集真实项目和跨平台证据 |
| 6. 工业化保障 | API 兼容、跨平台、自动化验证和发布 | 进行中 |

每个模块独立设计、交付和验证，不等待整个阶段同时完成。

## 当前建设方向

### 基线收敛

- 用实际游戏验证首版 API、生命周期、诊断和性能预算。
- 保持干净项目安装、完整替换升级、安全移除和导出验证可重复。
- public API 变化建立兼容证据和迁移说明。
- 按实际目标平台补充 Native AOT、Trimming 和跨平台验证。

### 由真实需求触发的候选

- Camera 第二视角或小地图输出。
- Audio 2D 空间线路。
- 独立核心示例。
- 远程资源、PCK/DLC、热更新或高级缓存扩展。

这些候选没有排期。所需输入集中在[待确认问题](待确认问题.md)，确认后必须先形成独立设计。

## 暂缓方向

- 集中接管所有 `_Process` / `_PhysicsProcess` 的 Tick 系统。
- 泛化协程或后台 Godot 对象任务框架。
- 全局大门面、自动程序集扫描、反射式插件发现和隐式依赖注入。
- 通用虚拟文件系统；现有日志、Save 和 Settings 继续使用各自受控路径。
- 网络、ECS、战斗、技能、AI 等具体领域框架进入 GoDo 核心。

## 后续发布批次

准备下一次对外发布时集中完成：

1. 确认语义化版本、最低 Godot 版本和最高已验证版本。
2. 复核固定的 `v0.7.0` 历史升级样本和兼容证据。
3. 通过统一发布门禁验证构建、回归、文档、API 基线和发布包生命周期。
4. 发布仅包含 `addons/godo_framework/` 的 ZIP、Git 标签和 `CHANGELOG.md`。
5. 在版本、说明和展示资源稳定后再评估 Godot Asset Library。

## 立项门槛

任何新模块或重大扩展在实现前必须回答：

1. 哪个重复痛点已经在真实项目出现？
2. Godot 原生能力和现有 GoDo 模块为什么不足？
3. 负责什么、明确不负责什么？
4. 依赖、生命周期、线程、失败语义和性能预算是什么？
5. 最小 public API 和兼容影响是什么？
6. 自动化、Godot 场景和目标平台分别如何验收？

使用[设计文档模板](../_模板/设计文档模板.md)记录答案，未确认的取舍进入[待确认问题](待确认问题.md)。
