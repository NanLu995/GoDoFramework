# GoDoFramework 项目总览

> 文档类型：基线
> 状态：当前
> 权威范围：框架定位、目标、非目标和长期设计原则
> 最近核对：2026-09-28
> 相关事实：[工程配置](../../GoDoFramework.csproj)、[架构基线](../01_架构/架构基线.md)、[模块状态](模块状态.md)

GoDoFramework 是建立在项目声明版本 Godot 4.x C# 之上的游戏开发框架，用于沉淀多个项目反复遇到的生命周期、通信、诊断、资源管理和运行时服务问题。

- Godot 负责节点、场景、资源、渲染、物理、音频和输入等引擎能力。
- GoDo 提供跨游戏可复用、可组合和可验证的工程机制。
- 具体游戏负责角色、战斗、数值、任务、剧情和其他业务规则。

框架不替代 Godot，也不以模块数量衡量成功。它的价值是减少重复代码、生命周期错误和跨系统耦合，同时允许业务直接使用 Godot 原生 API。

## 目标

1. 沉淀确有重复价值的事件、错误处理、资源、对象池和长期服务。
2. 保持框架与玩法边界清楚，依赖方向可见。
3. 贴合 Node、Resource、Signal、场景树和 Godot 主线程模型。
4. 支持渐进采用，避免可选模块成为隐式前置条件。
5. public API 具有明确失败语义、文档和与风险匹配的验证。
6. 只优化已经确认的热点，让生命周期、分配和性能预算可解释。
7. 建立兼容、迁移、诊断、自动化验证和可重复发布能力。
8. 所有稳定性结论都说明验证平台和证据。

## 非目标

- 不构建 ECS、依赖注入容器或另一套场景系统来取代 Godot。
- 不在 `GoDo.*` 中实现角色、战斗、技能、任务等具体玩法。
- 不屏蔽所有 Godot 原生 API。
- 不追求没有证据支持的“零 GC”或提前抽象。
- 不一次性建设全部候选模块。

## 设计原则

- **Godot 优先**：先组合 Godot 已有能力，再补齐工程缺口。
- **机制与业务分离**：框架提供机制，游戏定义玩法类型和业务事件。
- **小核心、可选服务**：Core 只保留地基能力，运行时服务独立存在。
- **依赖显式**：初始化和注册过程必须能够看出依赖；Services 不隐藏框架内部依赖。
- **失败可见**：使用异常、`Try...` 结果或结构化报告表达失败，不静默吞掉。
- **先验证再抽象**：先有真实痛点，再进入框架；经过实际场景验证后才收敛 API。
- **可演进交付**：兼容性变化必须说明迁移步骤和验证证据。
- **工业化而不膨胀**：工业级表示可预测、可诊断、可迁移和可验证，不表示大而全。
