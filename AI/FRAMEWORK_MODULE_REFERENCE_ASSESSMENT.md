# GoDoFramework 模块设计参考评估报告

> 评估对象：仓库根目录的《游戏开发框架模块设计参考》
> 评估基线：当前源码、工程配置、`AI/ARCHITECTURE.md`、`AI/FRAMEWORK_DESIGN_PLAN.md` 与各模块 `USAGE.md`
> 评估目的：判断参考建议在 GoDoFramework 中哪些已经实现、哪些值得继续建设、哪些应保持为可选扩展或业务能力，以及哪些不适合进入本框架。

## 1. 结论摘要

参考文档的核心判断与 GoDoFramework 当前方向高度一致：框架应统一跨项目机制、生命周期、失败语义和诊断，不应替代引擎，也不应把具体玩法下沉到 `GoDo.*`。现有 GoDo 已经覆盖参考文档“最小框架版本”中的主要基础能力，并且在资源、存档、数据表、错误处理、调试、失败回滚和验证方面比参考文档的概念示例更具体。

当前最需要避免的误判有两类：

1. **未实现不等于缺陷。** 资源引用计数、第二套缓存、通用 DI、通用状态机、完整 ECS、网络同步、战斗/技能/任务等内容，是 GoDo 有意不放进核心的边界。
2. **模块存在不等于建议已完整实现。** 例如 UI 已有完整基础管理，但数据绑定、通用动画、红点等仍属业务或扩展；Localization 已完成，但可访问性只有分散能力，还没有统一基线。

综合判断：

- **已经形成可靠实现**：运行时入口与服务注册、事件、错误、日志、资源加载、节点池、调度器、主场景切换、UI 基础管理、音频、输入、配置、数据表、存档、顶层 Procedure、主镜头编排、本地化、只读 Debugger、自动回归体系。
- **已实现核心边界，但原文中的高级能力没有全部覆盖**：应用生命周期、模块依赖管理、通用异步、资源生命周期、场景/关卡/世界流程、UI、音频、输入、配置数据、相机、本地化与可访问性、性能与生命周期诊断。
- **很好的建议，但当前尚未完成或只部分完成**：跨平台验证与发布门禁、应用前后台/暂停恢复的统一事实、可访问性基线、技术遥测扩展点、资源/任务所有权诊断深化、UI 安全区从业务约定提升为可复用约定、配置差异检查、按真实需求建设的网络传输层。
- **不适合进入 GoDo 核心**：具体玩法规则、战斗/技能/Buff、任务/背包/商城等领域模块、完整 AI、完整 ECS、自建引擎对象模型、镜头算法、产品埋点、GM 命令、远程资源/热更新/DLC 的核心内建实现。
- **适合可选集成**：Friflo ECS、Phantom Camera 已采用这种方式；未来网络后端、远程资源、DLC、AI、回放等也应采用相同原则，而不是扩张 Core 或 GoDoRuntime。

因此，参考文档不应被转换成“把缺失模块逐个补齐”的待办表。更适合 GoDo 的路线是：**先用真实游戏验证现有模块，优先补工业化和跨切面缺口，再让新的可选能力由真实需求触发。**

## 2. 评估口径

本报告使用以下状态：

| 状态 | 含义 |
|---|---|
| 已实现 | 原文建议已经有对应源码、公共契约和验证证据 |
| 部分实现 | 核心场景已覆盖，但原文列举的高级或细分能力仍有缺口 |
| 值得做但未实现 | 与 GoDo 定位相符，且可能有较高跨项目价值，但仍需真实需求或专项设计 |
| 后置候选 | 有复用价值，但当前没有足够真实用例，不应立即立项 |
| 引擎/项目负责 | Godot 或具体项目已经是更合适的责任主体 |
| 不适合核心 | 会引入玩法、产品或特定技术栈耦合，应留在业务层或可选包 |

“已实现”只表示已达到 GoDo 自己声明的边界，不表示原文罗列的所有扩展能力都应该继续塞入同一模块。成熟度仍以 [当前架构](ARCHITECTURE.md) 和对应模块 `USAGE.md` 为准。

## 3. 总体边界与分层判断

### 3.1 引擎、框架、业务、工具链

| 参考观点 | GoDo 现状 | 判断 |
|---|---|---|
| 框架负责跨项目问题，业务负责玩法 | `GoDo.*` 明确禁止角色、血量、子弹、关卡规则等概念 | 已落实，必须保持 |
| 引擎负责渲染、物理、节点、资源等基础能力 | GoDo 以 Godot 优先，不替代 Node、Resource、Signal、SceneTree | 已落实 |
| 工具链负责生产、检查和发布内容 | EditorPlugin、DataTable 编译前端、文档与验证脚本已侧挂存在 | 已落实，但正式发布流程仍在规划中 |
| 不重新实现渲染器、物理或完整动画系统 | 当前没有对应替代实现 | 已落实 |

GoDo 的实际分层是 `业务 → Runtime Services → Runtime Foundation → Core → Godot`，Editor、Debugger、Tools 和 Integrations 侧挂。这比参考文档的四层示意更贴合当前 Godot C# 工程。没有必要为了形式一致再增加一层空泛的 Engine Adapter；只有确有替换价值的输入、摄像机、平台设置等位置才建立适配边界。

## 4. 二十项核心能力逐项评估

### 4.1 应用启动与生命周期

**总体状态：部分实现，核心骨架已经可靠。**

- **已实现**：`GoDoRuntime.tscn` 唯一 Autoload；主线程记录；Core/Foundation 初始化；长期服务显式创建和注册；固定初始化顺序；退出时反向注销和清理；进程级未处理异常兜底；Procedure 表达启动、菜单、加载、游戏中、暂停、结算等业务顶层阶段；Demo3D 跑通完整小型游戏流程。
- **部分实现**：配置、数据表、输入绑定和玩家设置由业务启动流程显式加载，而不是 GoDoRuntime 自动执行。这是正确边界，不是缺陷。
- **值得做但未实现**：如果目标平台出现真实需求，可增加统一的应用前台/后台、窗口失焦、暂停/恢复、低内存警告等“事实通知”和生命周期契约；需先确认平台和 Godot 4.7.1 的实际通知语义。
- **后置候选**：异常启动恢复、启动步骤观测和恢复点。现有模块有结构化失败，但没有统一 Bootstrap 恢复编排。
- **不适合核心内建**：热更新检查、登录鉴权、玩家数据加载、首业务场景选择。它们应由业务 Procedure 或未来可选服务组织，GoDoRuntime 不应知道这些流程。
- **不建议采用**：让所有模块实现统一 `Update()`。GoDo 当前只让真正需要帧更新的服务启用对应 Process，符合原文避免空 Update 的建议。

### 4.2 模块系统与依赖管理

**总体状态：已实现符合 GoDo 规模的“显式组装 + 轻量注册表”。**

- **已实现**：按接口注册和查询、缺失查询、重复注册拒绝、实例匹配注销、退出清空、测试时显式替换；GoDoRuntime 中显式构造并按固定顺序注册；服务间依赖通过构造或初始化参数传入。
- **部分实现**：模块状态主要由各服务自身状态和 Debugger 快照表达，没有统一 `ModuleState` 模型。
- **有意不实现**：自动构造、反射发现、依赖图声明、拓扑排序、循环依赖检测、作用域容器、完整 DI。当前依赖数量和固定入口不值得引入容器复杂度。
- **判断**：原文偏好的“显式组装为主、轻量容器为辅”正是 GoDo 当前方案。Services 必须继续只服务业务层，不能退化为框架内部的全局对象仓库。

### 4.3 时间与更新调度

**总体状态：核心需求已实现，确定性时间和服务器时间明确不在首版。**

- **已实现**：`GameTime`、`UnscaledGameTime`、`RealTime`；Process/Physics 阶段；一次性和重复任务；取消、独立暂停/恢复；Owner 退出自动取消；异步等待；框架关闭清理；人工时钟回归；无到期任务时不遍历全部任务；Debug 快照。
- **对应原文**：帧阶段、固定物理阶段、受暂停/倍速影响的游戏时间、不受缩放的时间、定时器、延迟、取消、暂停、Owner 批量清理均已覆盖。
- **未实现**：独立 `UITime`、服务器校准时间、确定性 Tick/回滚时间、跨存档离线时间、持久化定时器。
- **判断**：独立 UI 时间可先由 Tween/动画和 `UnscaledGameTime` 解决；服务器时间和确定性模拟必须由联网或玩法需求触发，不能加入通用 Scheduler。

### 4.4 事件、消息与信号

**总体状态：已实现，并且使用边界比参考文档更明确。**

- **已实现**：类型化同步事件、一次性监听、优先级、稳定顺序、派发期间安全增删、同类型重入、监听者异常隔离、Node 自动解绑、纯 C# `EventScope`、跨模块事实通知、监听数与注册表诊断。
- **已落实原则**：命令/返回值使用直接调用；场景树局部关系优先 Godot Signal；一对多事实通知使用 EventChannel。
- **有意不实现**：请求—响应事件、异步事件总线、跨线程事件总线、无边界的全局业务事件仓库。
- **可改进但不紧迫**：Debugger 已展示监听统计；只有真实排障证明需要时，才考虑显示更细的订阅来源，避免为了诊断长期强持有订阅者。

### 4.5 异步任务系统

**总体状态：模块化实现较强，不需要再造统一协程框架。**

- **已实现**：Resource、Scene、UI、Audio、DataTable、Procedure 和 Scheduler 各自提供异步 API；取消、进度、结构化错误、主线程完成、退出清理和部分请求合并已有明确契约；ProcedureContext 提供激活期 `LifetimeToken`。
- **部分实现**：资源加载会共享同 Key/类型的任务；其他模块按自身语义选择并发拒绝、latest-request-wins 或事务发布，没有全局重复请求合并策略。这是合理差异。
- **值得做但未实现**：若多个模块反复出现相同需求，可抽取非常小的超时/重试策略工具；在此之前应由业务流程显式组合 Scheduler 与 CancellationToken。
- **有意不实现**：泛化协程框架、全局 Task 注册表、自动主线程切换、用 `Task.Run` 操作 Godot 对象。
- **当前诊断缺口**：Debugger 能观察模块自己的活动请求和 Scheduler，但不能列出所有业务 Task；若以后建设，只能要求显式登记，不能假装能追踪任意 .NET Task。

### 4.6 资源管理

**总体状态：资源加载核心已实现；参考文档中的高级缓存清单大多不适合 ResourceHub。**

- **已实现**：`ResourceKey` 的 `res://`/`uid://` 契约、同步加载、线程化异步加载、类型检查、进度、同 Key/类型请求合并、失败异常、语义 ResourceManifest/Registry、Godot 缓存复用、Shutdown 取消、活动请求与有界历史诊断。
- **部分实现**：语义 ID 可承担基础资源标签/注册用途；Audio 提供资源准备；UI、Scene、Config 通过 ResourceHub 加载。没有建立统一资源分组、预加载清单或场景资源作用域。
- **有意不实现**：第二套引用计数、强引用缓存、LRU、弱引用缓存、递归释放、手动 Unload、重新包装依赖资源。Godot 已有 Resource 缓存和引用语义，再造一套会产生所有权冲突。
- **未来独立扩展**：远程下载、版本校验、PCK/DLC、热更新、下载重试、内存预算。只有真实项目提出包选择、挂载、回滚和安全要求后再设计。
- **不采用原文示例的原因**：`LoadHandle.Release()` 适合拥有独立资源后端的框架；GoDo 基于 Godot Resource，不应伪造一套与引擎生命周期并存的 Handle/Release 语义。

### 4.7 对象池

**总体状态：Godot Node 场景已经完整实现。**

- **已实现**：`NodePool<T>`、PackedScene 实例化、预热、按需扩容、空闲容量、Acquire/Release 回调、重复/外部归还检测、异常回滚、Clear/Dispose、活动对象强制清理、Debug 弱引用登记和池统计。
- **已落实原则**：池化必须由实际创建成本或高频需求证明；状态由 `IPoolable` 显式重置；不默认池化所有对象。
- **未实现**：通用纯 C# 泛型池、集合池、网络缓冲池、全局/场景池注册服务、详细租借堆栈和泄漏来源。
- **判断**：这些不应预先加入。纯 C# 池应由具体热点证明；全局池服务会把明确实例所有权重新隐藏起来。

### 4.8 场景、关卡与世界流程

**总体状态：主内容场景切换已实现；Level 和 Game Flow 被正确拆开。**

- **已实现**：单主场景异步加载和安全替换、进度、并发拒绝、旧场景保留、加载/实例化/提交失败阶段、取消、成功后旧场景释放、Debug 诊断。
- **已实现的职责拆分**：SceneService 只做 Scene；Procedure 组织主菜单、加载、游戏中、暂停、结算等 Game Flow；具体 Level 初始化和玩家出生属于业务；UI Loading 由业务通过 UI 组合。
- **未实现**：叠加场景、多世界、统一 Loading 页面、跨资源进度聚合、关卡数据模型、场景服务集合初始化、自动失败回退场景、完整切换事务编排。
- **值得做但需真实需求**：叠加场景和进度聚合。它们会改变所有权、失败回滚和卸载语义，不能从单主场景 API 自然推断。
- **不适合 SceneService**：登录、存档、业务资源预载、玩家出生、结算等强顺序流程；继续交由 Procedure 和业务类直接编排。

### 4.9 UI 框架

**总体状态：基础管理已实现，展示内容和复杂 UI 架构保持业务化。**

- **已实现**：Inspector 配置和语义 `UiId`、同步/异步创建、打开/关闭/查询、四层显示、View/Modal 返回栈、返回操作、Modal 指针遮挡、焦点隔离与恢复、单实例约束、可选实例复用、场景层自动清理、请求取消、所有权 `UiScope<TView>`、失败回滚、Debug 诊断。
- **与原文分类的映射**：Scene≈HUD，View≈Screen，Modal≈Popup，Overlay 可承载 Toast/Loading/引导；System 级提示没有被硬编码成独立业务层。
- **Demo3D 已提供但不属于核心服务**：Loading、Pause 和结算界面；这说明机制与具体表现已分离。
- **未实现**：通用动画系统、红点系统、通用列表、数据绑定、Presenter/响应式/MVVM 强制架构、自动本地化刷新、世界空间 UI、完整输入竞争仲裁、通用窗口互斥规则、分辨率适配服务。
- **值得继续验证**：安全区组件能否在多个真实项目重复使用；键盘/手柄返回和 Modal 输入阻断；缓存实例的状态重置与内存预算。
- **不建议加入核心**：强制统一 MVVM、具体 Toast 样式、红点规则、业务 Loading 流程和复杂动画编排。

### 4.10 音频系统

**总体状态：非空间与 3D 播放核心已经很强。**

- **已实现**：BGM、非空间 SFX、3D SFX、音量分组、0 音量静音语义、立即切换、等功率 Crossfade、淡出、暂停恢复、资源准备、独立 Voice 池和预热、全局/单 Key 并发限制、优先级抢占、Handle 停止、静态坐标和 Node3D 跟随、设置持久化、Debugger 状态与性能基准。
- **部分实现**：UI/战斗音效都可通过 SFX 播放，但不是硬编码类别；语音和环境音可由业务使用现有能力，当前没有独立流控或总线契约。
- **未实现**：相同音效冷却、独立 Voice/环境音模型、AudioStreamPlayer2D 路线、通用播放队列、音频本地化服务。
- **后置候选**：2D 空间 SFX 已在计划中；真实项目和跨平台验证优先于继续扩 API。
- **不适合音频核心**：何时播放技能音效、随机音高策略、具体混音内容和资源选择。

### 4.11 输入系统

**总体状态：语义输入、Context 和重绑定已经实现。**

- **已实现**：语义 Action、Bool/1D/2D/3D 当前帧、键鼠/手柄/触摸设备类别、Context 栈、Overlay/Exclusive 竞争规则、活动设备变化、运行时重绑定、冲突查询、默认恢复、Save 持久化、文本提示查询、可替换后端、零分配热读取和 Debug 诊断。
- **部分实现**：触摸作为设备类别和后端能力存在，但移动端真机尚未完成；UI 与玩法输入竞争需要业务正确切 Context；可访问性目前覆盖改键，不等于完整无障碍输入方案。
- **明确不支持**：本地多人设备分配、手势、多点触控抽象、虚拟摇杆、输入历史、录制/回放、连招窗口、格斗/节奏判定、网络预测、确定性重演。
- **判断**：高级输入大多玩法或联网相关，继续留在业务/可选扩展。只有多项目重复验证后才考虑扩大核心。

### 4.12 配置与数据表

**总体状态：强类型 Resource 配置与大型表格工具链均已实现。**

- **Config 已实现**：Godot Resource 强类型加载、内容校验、唯一键只读索引、明确失败语义；不建立第二套缓存。
- **DataTable 已实现**：UTF-8 CSV、JSON Schema、类型转换、主键索引、默认值、必填/空值、数值与长度范围、枚举、跨表外键、确定性二进制、强类型 C# 生成、逐表进度、事务发布、缓存/卸载、编辑器操作、Client/Server audience、Manifest 兼容比较、导出过滤和发布包装门禁。
- **部分实现**：`schema_version`、`protocol_version` 和 Manifest 摘要提供版本/兼容基础，但没有通用运行时热重载或数据迁移系统；多语言字段可由项目 Schema 表达，但不是框架专门类型。
- **未实现**：直接 Excel 导入、JSON 数据表输入、配置热重载、可视化配置差异、远程配置、自动资源存在性验证、任意跨表业务矛盾检查、超大表分块。
- **非常好的后续建议**：配置差异检查和更多构建期业务验证。应以 DataTable Schema 的可表达规则或项目自定义验证器扩展，不要把业务规则写进 GoDo。

### 4.13 存档系统

**总体状态：可靠容器核心已经实现，业务迁移边界清楚。**

- **已实现**：安全槽位、多存档、容器版本、业务数据版本、SHA-256 完整性、临时文件、提交前复读校验、正式档/备份恢复、损坏检测、大小上限、Codec 边界、NotFound 正常结果、Settings 独立槽位。
- **版本迁移**：由业务 `ISaveCodec<T>.Decode(payload, dataVersion)` 处理，符合“独立存档模型 + 显式迁移”的建议；框架不自动序列化运行时对象图。
- **未实现**：自动存档调度、检查点策略、云存档、压缩、加密、槽位 UI。
- **判断**：自动存档和检查点是业务流程；云存档依赖平台账户；压缩/加密只有真实体积、隐私或防篡改目标出现后再做策略设计。它们不应成为 Save 首版默认复杂度。

### 4.14 网络通信

**总体状态：未实现。**

- **原文能力均未作为 GoDo 模块提供**：HTTP、WebSocket/TCP/UDP、序列号、请求响应、超时、取消、重试、心跳、重连、鉴权、序列化、协议版本、错误码、网络状态、流量统计、请求日志、模拟网络、延迟/丢包、幂等。
- **已有可复用地基**：Scheduler、ErrorHub/LogHub、Procedure、DataTable 的 Client/Server Manifest 和可取消异步契约可以支持未来网络层，但不等于网络已实现。
- **判断**：网络传输层是“非常合理但必须由目标项目触发”的候选。单机框架不应为了清单完整性预建完整联网栈；HTTP 服务、实时传输、锁步/预测也不应被塞入同一个接口。
- **未来设计原则**：传输与业务消息分离；结构化错误交给流程决定重试/退出/UI；按具体协议和平台选择后端；先有至少一个真实在线项目再确定 public API。

### 4.15 状态机与流程系统

**总体状态：顶层流程已经实现，通用状态机被有意拒绝。**

- **已实现**：Procedure 的异步 Enter/Exit、串行切换、并发拒绝、首请求仲裁、激活期 Token/EventScope/逆序清理、结构化失败阶段、Debug 诊断和 Demo3D 的完整业务流程。
- **未实现**：通用 FSM、HFSM、条件图、状态历史、黑板、反射发现、流程栈，以及角色/AI/UI/战斗共用状态机。
- **判断**：当前做法完全符合原文“一套状态机不应统治所有系统”的提醒。只有某类局部状态机在多个游戏中重复出现，才考虑独立扩展，不能把 Procedure 泛化。

### 4.16 实体与组件模型

**总体状态：核心使用 Godot Node；Friflo ECS 作为可选集成已完成首版。**

- **已实现**：可选 `EcsWorldHost` 提供场景级 World 所有权、Process/Physics 单阶段驱动、暂停/Shutdown、Debug 快照和规模基准。
- **有意不实现**：GoDo 自建 Entity/Component/Query/System、服务器共享逻辑层、完整 ECS、自动系统发现、ECS 存档封装、实体编辑器。
- **判断**：这正是适合 GoDo 的实现。框架不替代 Godot Node，也不包装 Friflo 全部 API；需要大量同构数据处理的项目显式安装可选包。

### 4.17 属性、Buff、技能与战斗

**总体状态：未实现，且不适合 GoDo 核心。**

属性、修饰器、Buff/Debuff、技能流程、冷却、消耗、选目标、伤害管线、效果、标签、战斗事件、仇恨、战斗日志和回放均属于游戏类型和玩法规则。GoDo 当前明确禁止这些概念进入 `GoDo.*`。

如果未来要做 RPG、卡牌或 MMO，可建立独立 `Gameplay.*` 包，依赖 GoDo 的事件、调度、数据表、存档和诊断；不能反向让 GoDo 核心依赖领域包。

### 4.18 AI 框架

**总体状态：未实现，适合作为按项目选择的扩展。**

FSM、HFSM、行为树、Utility AI、黑板、感知、目标选择、寻路适配、AI 降频、可视化和回放都没有进入 GoDo。原文列出的方案差异本身说明这里不存在一套足够稳定的通用核心接口。

建议继续使用 Godot/第三方能力或业务包。若出现多个项目的共同需求，优先做窄适配和诊断，不先造一套综合 AI 平台。

### 4.19 相机系统

**总体状态：上层主镜头编排已实现，底层算法由 Godot/插件负责。**

- **已实现**：语义 CameraId、Rig 注册/注销、主镜头激活、恢复历史、失败回滚、跨场景同 ID；Phantom Camera 可选适配和第三人称预设。
- **由插件/业务负责**：跟随、平滑、震动、缩放、边界、多目标构图、过场参数、碰撞、效果叠加。GoDo 不重复封装 Phantom Camera API。
- **未实现**：小地图/监控 SubViewport、分屏、第二视角输出、通用能力查询。
- **值得做但需输入**：第二视角已进入候选；必须先确定 2D/3D、SubViewport 所有权、渲染层、分辨率和更新频率。

### 4.20 本地化与可访问性

**总体状态：本地化首版完成；可访问性只有分散基础，尚无统一框架基线。**

- **本地化已实现**：TranslationServer 薄封装、可用 Locale、参数化翻译调用、复数、上下文、运行时切换、变更事件、默认回退、伪本地化诊断、Settings 持久化。
- **由 Godot/项目负责**：PO/CSV 解析、字体和 fallback Theme、Control 自动文本/布局方向、图片/音频/场景本地化。
- **未实现或未完整验证**：动态语言包、专门的性别/语法变体抽象、自动缺失翻译报告、文本溢出扫描、RTL 全面人工验收、字体切换策略。
- **可访问性已有基础**：输入重映射、文本提示、焦点管理，以及 Demo3D 的语言设置展示。
- **可访问性缺口**：字体缩放、色盲/高对比、长按替代连点、减弱镜头震动、字幕规范、屏幕阅读提示和操作辅助没有统一契约。
- **非常好的建议**：尽早建立“可访问性设计基线和项目检查清单”，但不要急于创建一个包办 UI、输入、相机、音频的巨型 AccessibilityService。先让各模块暴露必要能力，再由项目设置和 UI 组合。

## 5. 开发与调试能力逐项评估

### 5.1 统一日志

**状态：首版完成，仍有少量生产化缺口。**

- **已实现**：Debug/Info/Warning/Error/Fatal、模块分类、UTC 时间、上下文、异常链、本地滚动文件、有界后台写入、Debugger 搜索/筛选/分页、重复聚合、速率限制、Debug/Release 裁剪、Reporter 扩展。
- **部分实现**：`context` 是有界字符串，不是任意结构化字段集合；帧号和对象上下文没有统一字段；标签可用模块和上下文表达，但不是独立模型。
- **未实现**：生产远程日志 Reporter、统一敏感字段脱敏策略、跨平台文件写入完整验证。
- **建议**：远程上报和脱敏要一起设计，并由实际后端、隐私政策和采样预算触发；不要只添加一个同步网络 Reporter。

### 5.2 游戏内调试面板

**状态：只读诊断已形成稳定基线。**

- **已显示**：FPS、Godot/.NET 内存、引擎性能指标、系统环境、当前 Scene、资源活动请求与历史、Pool、Event、Services、Input、Scheduler、Audio、DataTable、UI、Procedure、运行链路、日志和错误，可选 ECS。
- **不显示**：玩家位置、当前 Buff、网络延迟、服务端环境等未存在或属于业务的数据。
- **有意不实现**：调试命令、GM 命令和修改游戏数据。Debugger 定位是只读，避免成为新的全局管理器或 Release 安全入口。
- **可选方向**：需要命令控制台的具体游戏可建立业务 Debug 扩展；必须与只读框架诊断、构建裁剪和权限控制分开。

### 5.3 性能监控与埋点

**状态：本地技术诊断部分实现，通用遥测和产品埋点未实现。**

- **已实现**：Godot Performance 指标、约 30 秒有界趋势、模块状态快照；Scheduler、Audio、UI、ECS、DataTable 等专项性能/内存基准。
- **未实现**：通用方法耗时 API、首屏/场景切换统一指标、卡顿帧捕获、网络失败率、崩溃上下文包、远程技术遥测、产品行为埋点。
- **判断**：技术遥测与产品埋点必须分开。技术遥测可在真实线上诊断需求出现后，通过有界采样和 Reporter/适配器扩展；产品埋点属于具体游戏和分析平台，不进入 GoDo Core。

### 5.4 错误处理

**状态：结构化错误基础已经很强。**

- **已实现**：等级、模块、消息、上下文、异常/根因、UTC 时间、调用栈、监听、Reporter、后台队列、递归保护、监听隔离、未处理异常兜底；模块异常还保留资源键、槽位、阶段等专用上下文。
- **部分实现**：原文的 Code、Category、UserMessageKey、IsRetryable 没有统一放入一个全局 `GameError`。当前由模块异常类型和业务流程决定恢复/重试/UI，这是合理的分层。
- **未实现**：统一错误码目录、玩家消息映射、弹窗去重、全局重试策略。
- **判断**：现在不应把所有异常压成一个庞大错误 DTO。网络或线上服务出现后，可以为跨边界错误建立稳定码；玩家提示和恢复策略仍由业务流程决定。

### 5.5 资源和生命周期诊断

**状态：部分实现，且是参考文档中最值得继续深化的方向之一。**

- **已实现**：活动资源请求、请求历史、Scheduler 活动/暂停/Owner 取消统计、Event 监听统计、Pool 活动/空闲、UI 实例/缓存/失效节点、Scene/Procedure 状态、DataTable 缓存和可选 ECS 宿主。
- **部分实现**：能回答模块级“现在有什么”，但不能总是回答“业务中的哪个对象为什么还持有它”。
- **未实现**：Godot Resource 的完整引用来源、任意业务 Task、每个计时器的调用堆栈、每个订阅者来源、未归还对象的租借堆栈、场景卸载后通用残留扫描、内存快照标签。
- **建议**：逐个模块增加低成本、Debug-only、显式所有权证据；不要建立全局强引用注册表，也不要承诺追踪引擎和 .NET 中所有引用。

### 5.6 自动化测试支持

**状态：框架自身验证较完整，面向任意游戏的测试工具箱只部分实现。**

- **已实现**：模块回归场景、人工时间、假输入后端、测试平台适配器、临时独立存档槽、资源/配置/DataTable fixture、场景冒烟、Headless runner、Debug/Release 编译、性能基准、插件/包/文档验证、Demo3D 完整流程回归。
- **部分实现**：Services 可手动替换接口实现；DataTable/Save/Settings 有内存或测试 Codec/fixture，但没有统一 TestHost。
- **未实现**：模拟网络、通用内存资源提供器、输入录制回放、统一固定随机源、战斗模拟工具、通用业务测试替身包。
- **判断**：网络和战斗相关测试能力应随对应模块出现。当前更重要的是把已有回归纳入稳定的 CI/发布门禁，而不是先做抽象 TestKit。

## 7. 原文“不建议进入通用框架”的内容

### 7.1 具体玩法规则

攻击力计算、卡牌抽取、掉落概率、升级曲线、关卡胜利条件和角色连招均未进入 `GoDo.*`。当前架构完全符合建议。

### 7.2 具体美术表现

技能特效、按钮动画、Boss 出场镜头、角色受击材质变化均由业务或资源数据决定。GoDo 只提供 UI、Audio、Camera、Resource 等播放和组织机制，边界正确。

### 7.3 为“可能的未来”过度抽象

| 原文风险 | GoDo 当前判断 |
|---|---|
| 单一资源后端却设计多层 Provider | 已避免；ResourceHub 直接复用 Godot |
| 尚未联机却预建网络同步 | 已避免；Network 未立项 |
| 单一 UI 却建立高度动态插件系统 | 已避免；UiService 提供固定基础机制 |
| 少量单位却强制完整 ECS | 已避免；Friflo 只作为可选场景集成 |
| 未支持 Mod 却先造脚本沙箱 | 已避免 |

## 8. 能力进入框架的判定标准

参考文档的正反信号与 GoDo 设计原则一致，可以直接吸收为评审问题：

- 多项目重复、需要统一生命周期/资源所有权、跨平台适配、统一错误/诊断/测试、业务重复实现易错、接口趋于稳定时，才考虑进入框架。
- 只服务一个玩法、需求频繁变化、项目差异大、接口比直接调用更复杂、只有一个调用方、没有第二个真实用例时，留在业务层。
- “第一次业务实现，第二次观察共同点，第三次考虑抽取”适合作为默认经验规则，但不是机械门槛。

GoDo 还应增加两个项目特有问题：

1. Godot 原生 Node/Resource/Signal/SceneTree 是否已经足够？
2. 新抽象是否会建立第二套缓存、生命周期、场景或输入模型？

只要第二个问题答案为“会”，就必须有明确、可验证的收益才能继续。

## 9. 推荐分层与 GoDo 实际分层

| 参考层 | GoDo 对应 | 评价 |
|---|---|---|
| Gameplay | `GoDo.*` 之外的游戏代码、Demo3D 示例 | 清楚 |
| Feature Packages | 未来 `Gameplay.*` 或独立插件；现有 Friflo/GuideInput/Phantom 属技术集成 | 机制已具备，领域包尚未建设且不急需 |
| Core Framework | Core + Runtime Foundation + Runtime Services | 已按依赖方向细分 |
| Engine/Platform Adapters | Godot 直接能力、Settings 平台适配、Integrations 后端 | 按真实替换点建立，不单独造空层 |

依赖方向保持单向；业务若向框架提供能力，应通过窄接口或适配器注册。GoDoRuntime 继续只初始化和注册，不成为 GameApp/流程大管家。

| 对象池 | 已实现 |
| 本地化 | 已实现首版 |
| 输入映射 | 已实现首版 |
| 网络封装 | 未实现，待真实在线项目 |
| 配置验证 | 已实现，DataTable 工具链较完整 |
| 性能指标 | 本地 Debugger 和专项基准已实现；远程遥测未实现 |
| 自动化构建 | 有 runner、导出包装、包和文档验证；正式 CI/版本发布流程仍在规划 |
| 测试替身 | 按模块已有人工时钟、假后端和适配器；没有统一 TestKit |

### 10.3 第三阶段：领域扩展

技能/Buff、任务、对话、背包、AI、联机同步、回放和活动系统均未进入核心，符合 GoDo 的通用框架定位。是否建立独立包必须由目标游戏类型和至少一个真实实现决定。

## 11. 七类常见陷阱检查

| 陷阱 | 当前表现 | 风险与建议 |
|---|---|---|
| Manager 泛滥 | 使用职责明确的 Hub/Service/Controller/Codec；依赖规则清楚 | 低；继续限制 Services 用途 |
| 全局事件总线滥用 | 明确“事实用事件、命令用调用、局部用 Signal” | 低；继续补诊断而非扩大事件功能 |
| 过度封装引擎 | Resource/Localization/Camera/Input 均只补真实缺口 | 低；新模块继续先证明 Godot 原生不足 |
| 生命周期不明确 | 绝大多数模块有 Owner、Token、Scope、Shutdown 和失败语义 | 中低；业务 Task 和少数跨模块所有权仍难观察 |
| 框架依赖具体游戏 | `GoDo.*` 禁止玩法概念 | 低；Demo3D 示例不能反向进入框架 |
| 为通用性增加大量配置 | 当前 public API 多采用语义类型和小型 Options | 中低；Audio/UI 的 Options 后续仍需监控复杂度 |
| 只设计正常流程 | 大量回归覆盖取消、损坏、并发、回滚、关闭和失效对象 | 低；前后台、低内存和跨平台异常路径仍待目标平台验证 |

## 12. “优秀框架”评价标准逐项检查

| 原文标准 | 评价 |
|---|---|
| 生命周期明确 | 强；入口、服务、节点、请求和退出顺序均有契约 |
| 依赖关系可追踪 | 强；架构规则和显式组装清楚，Services 边界受限 |
| 资源所有权明确 | 中强；ResourceHub 不伪造所有权，Pool/UI/Procedure 明确；Godot Resource 引用来源不可完全追踪 |
| 异步操作可取消 | 强；主要异步模块均有取消或明确并发语义 |
| 错误不会静默丢失 | 强；异常、结果或 ErrorHub 三选一 |
| 模块可单独测试 | 强；已有模块级 Headless 回归 |
| 调试时可观察内部状态 | 强；Debugger 已形成稳定基线 |
| 简单功能不被迫采用复杂架构 | 强；Godot 原生能力可直接使用，可选模块不成为前置条件 |
| 业务不需要绕过框架 | 中强；已覆盖常见基础能力，仍需真实项目持续验证 |
| 新成员能较快理解 | 中；文档丰富，但模块数量和内部资料较多，需要继续优化上手路径 |
| 删除模块不会牵动整个项目 | 中强；服务和 Integrations 边界较好，但 GoDoRuntime 仍集中注册长期服务 |
| 不依赖大量全局单例 | 中强；静态 Core Hub 有明确职责，长期服务按接口注册 |
| 不把玩法写进核心 | 强 |
| 支持当前需求而非想象需求 | 强；设计计划明确先验证再抽象 |

## 13. 建议吸收事项与当前状态

以下建议按 GoDo 当前阶段排序，不等同于立即开发模块：

### P0：先收敛现有基线

1. **跨平台与真实项目验证**：Settings、Scheduler、Input、Localization、Audio 3D 跟随、DataTable、Debugger 等已有明确待验证项。它比新增 Network/AI 更能提升“工业级”可信度。
2. **自动化与发布门禁**：本地统一门禁已串联 Headless runner、Debug/Release 编译、文档、干净核心包、DataTable 可靠导出和发布归档；Core 与 Docs GitHub Actions 已在 Push/PR 中复用轻量阶段和 API 兼容检查，后续补升级、移除和正式版本发布流程。
3. **API 兼容与迁移纪律**：public API 规范化基线、删除与签名变化门禁、显式基线更新流程已完成；后续补齐正式弃用周期、逐版本迁移说明与升级/移除验收。

### P1：跨切面质量能力

1. **可访问性基线**：先形成设置项、UI、输入和相机的检查清单与最小接口约定；至少覆盖字体缩放、高对比/色盲、减少镜头震动、字幕、长按替代和屏幕阅读提示的项目责任边界。
2. **生命周期诊断深化**：Scheduler、Event、Pool、UI 及 Resources、Scene、Procedure、Audio、DataTable 的低成本 Owner、来源或活动年龄证据已完成当前范围，保持 Debug-only、有界、按需采集；新的追踪项继续由真实泄漏问题触发。
3. **应用级生命周期事实**：目标平台确定后，验证 Godot 前后台、窗口焦点、暂停恢复和低内存通知，必要时增加窄事件契约，不创建大而全 ApplicationService。
4. **配置差异与自定义验证扩展**：优先允许项目在构建期追加业务校验；是否需要通用 diff 报告由真实数据工作流决定。

### P2：由真实项目触发的独立候选

1. 网络传输与请求层。
2. 远程资源、PCK/DLC 和热更新。
3. Camera 第二视角/SubViewport。
4. Audio 2D 空间线路。
5. 技术遥测 Reporter 与崩溃上下文包。
6. 叠加场景和多资源加载进度聚合。

这些候选在立项前都应重新回答：真实痛点是什么、Godot 原生能力为何不足、所有权和失败语义是什么、是否形成第二套缓存/生命周期、Debug 与 Release 成本如何、哪些平台已经验证。

## 14. 明确不建议纳入当前路线的事项

- 为追求模块齐全而新增通用 Network、AI、FSM、ECS、文件系统或异步框架。
- 给 ResourceHub 增加引用计数、LRU、弱缓存、手动 Release 等第二套资源生命周期。
- 把 Procedure 泛化成角色、AI、UI、战斗共用状态机。
- 把 UI 扩展成强制 MVVM、红点、商城、引导和具体 Loading/Toast 表现集合。
- 把 Debugger 变成可修改运行时状态的 GM 控制台。
- 把产品行为埋点混入技术性能监控。
- 把登录、鉴权、玩家数据和热更新塞入 GoDoRuntime。
- 在没有目标平台和真实在线项目时承诺云存档、支付、联网同步、防作弊或远程热更新。

## 15. 最终建议

这份参考文档最有价值的不是模块清单，而是四个判断原则：边界清楚、生命周期明确、失败可见、先有真实需求再抽象。GoDo 已经在这四点上建立了较好的基础。

下一阶段应将其作为**审查清单**，而不是**功能采购清单**：

1. 用真实游戏和目标平台验证现有模块；
2. 把发布、兼容、迁移和自动化门禁补齐；
3. 优先改善可访问性与生命周期诊断等跨切面质量；
4. 网络、热更新、DLC、AI 和领域系统继续保持独立、可选、需求驱动；
5. 任何新增模块都继续遵循“小核心、显式依赖、Godot 优先、机制与业务分离”。

按此路线，GoDo 不需要成为参考文档中所有能力的集合；它更应该成为一套对生命周期、依赖、资源、失败和验证有清晰承诺的 Godot C# 工程框架。
